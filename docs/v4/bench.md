# v4 — the bench

> How we know a deck is good: 12 briefs, the baselines every run is compared against, a wall a human scores, and what each run records. Automated gates cannot see design ([../findings.md](../findings.md) → Process), so the wall is the gate at every phase exit.

---

## Briefs

`bench/briefs/*.json`. Twelve founder and sales briefs across 10 industries:

| Deck type | Count |
|---|---|
| Pitch (seed → Series B) | 4 |
| Sales (SaaS → enterprise, agency, hardware) | 3 |
| Launch | 2 |
| Investor update, with real-shaped metrics | 2 |
| Partnership proposal | 1 |

- **Half include pasted data**; the other half rely on research.
- **Every brief has a frozen outline.** Phases 22 and 23 build from the frozen outlines, so their walls measure design and not content. From phase 24 the content engine writes the outlines.
- **The smoke set** is 3 briefs: one pitch, one sales, one investor update.
- The five golden briefs from v1's acceptance run (`api/pipeline/acceptance/briefs.py`) are carried over where they fit.

## Baselines

Every wall shows our decks next to:

| Baseline | What it is | Why |
|---|---|---|
| **One shot** | The same best model, asked once for "a 10-slide HTML deck" from the brief. All 12 briefs | If the engine cannot beat a single prompt, the orchestration is overhead |
| **Gamma** | The same brief in Gamma, exported. 6 briefs, generated by the owner | The competitor the product is measured against |
| **v3** | The three `samples/*.html` decks, screenshotted before phase 21 deletes them | Where we started |

## The wall and the rubric

`python -m cli wall` builds one static HTML page: every slide of every deck as a screenshot grid, with **blind, shuffled labels**. Key presses record ratings into `ratings.json`.

Per deck, 1–5:

| Criterion | The question |
|---|---|
| Designed | Does it look designed, or like a template or an AI default? |
| Says something | Would the audience learn and remember a specific argument? |
| Varied | Do the slides differ from each other while reading as one deck? |
| Distinct | Could this deck be mistaken for another deck on the wall? |
| Usable | Would you present or send it with ≤2 fixes? |

Plus a **defect tally**: visible defects the owner spots. Any defect that no metric flagged becomes a new metric.

## What a run records

`bench/runs/<date>-<sha>/` (ignored by git). One summary row per run is appended to `bench/results.md`, which is committed.

- Git sha, prompt versions, pinned model ids.
- Cost per deck (median, p90) and by stage, from the ledger.
- Latency per deck (median, p90) and time to first slide.
- Slides defect-free, repaired, exemplar-filled and flagged (%).
- Distinct archetypes per deck; fingerprint overlap between decks.
- Content evals ([content.md](content.md) → Evals).
- Export size (median).
- The owner's ratings and defect tally.

**Cadence and spend (estimates):**

| Run | When | Cost |
|---|---|---|
| Smoke (3 decks) | While iterating | ≈ $3–5 |
| Full (12 decks) | Phase exits only | ≈ $15 |
| Phase 22 in total | — | Capped at $100 |

## Budgets

Per 10-slide deck. **Estimates**, assuming Sonnet-class list prices of $3 in / $15 out per million tokens and cache reads at 0.1×. Prices are checked at phase 21, and the real numbers are measured at phase 22.

| Stage | Cost | Latency |
|---|---|---|
| Interview | under $0.01 | 3–5 s |
| Research (≤30 results) | $0.12–0.20 | 10–20 s |
| Outline | $0.05–0.10 | 25–45 s |
| Theme and style tiles | $0 | ~3 s |
| Notes | $0.03–0.05 | in parallel |
| Slides (cache warmed by slide 1, then 5 in parallel) | $0.40–0.80 | 60–120 s |
| Repairs (~3) | $0.10–0.25 | +30–60 s |
| Images (3–4, plus the text check) | $0.10–0.25 | in parallel |
| QA and export | $0 | ~1 s per slide |
| **Total** | **≈ $0.80–1.70** (up to ≈ $2 on an Opus-class design model) | **≈ 2.5–4 min; first slide 50–70 s after approval** |

**Targets the phases gate on:** median ≤ $2, p90 ≤ 5 minutes, first slide ≤ 60 seconds (median), median export ≤ 6 MB.
